    1. 答题策略

    SAP 的难点不在知识点本身，而在 题干长（每题 150–300 字）、选项都"能用"，你需要选出最符合约束条件的那个。

    四步法

    1. 先读问句（最后一句）：找出约束词——"最具成本效益"、"运维开销最少"、"最少停机时间"、"最安全"、"最快"。
    2. 圈出硬性条件：RTO/RPO 数值、合规要求、现有技术（Oracle、SMB、VMware、AD）、带宽和时间窗口、"不能修改应用代码"。
    3. 排除法：先划掉违反硬性条件或技术上不成立的选项（例如 VPC 对等的传递路由、网关端点从本地访问）。
    4. 两两比较剩余选项：通常剩 2 个，差异往往在一个细节——托管 vs 自建、同步 vs 异步、一次性 vs 持续。

    约束词 → 倾向答案

    题干约束倾向警惕
    LEAST operational overhead全托管、Serverless、原生功能（Organizations、Control Tower、Backup、SSM）自建 EC2 脚本、cron、自定义 Lambda 轮询
    MOST cost-effectiveSpot、Savings Plans、S3 生命周期、Intelligent-Tiering、按需关停、Graviton为低频场景预置大量容量；多余的 NAT/DX
    MOST secure / least privilegeIAM 角色 + 临时凭证、SCP、KMS CMK、PrivateLink、VPC 端点长期 Access Key、0.0.0.0/0、共享凭证

    No code changesRehost/Replatform；RDS Proxy、ElastiCache 作为旁路重构为微服务、改用 DynamoDB
    Near real-time / 秒级Kinesis Data Streams、EventBridge、DynamoDB StreamsFirehose 有缓冲（秒到分钟）；批处理

    3. 域 1：组织复杂性设计 26%

    考察任务：网络连通性策略、规定的安全控制、可靠且有弹性的架构、多账户环境、成本与可视化控制。

    3.1 AWS Organizations 与多账户治理

    核心概念

    • 管理账户（Management account）：付款、创建账户、管理策略。最佳实践：不在管理账户运行工作负载。
    • OU：按职能/安全边界设计，常见结构：SecurityInfrastructureWorkloads/ProdWorkloads/SDLCSandboxSuspendedPolicy Staging
    • 委派管理员（Delegated administrator）：把 GuardDuty、Security Hub、Config、Firewall Manager、IAM Access Analyzer 等服务的管理权交给 Security 账户，避免使用管理账户。
    • 所有功能（All features）模式才能使用 SCP 等策略；仅"合并账单"模式不行。

    策略类型对比

    策略作用对象要点
    SCP成员账户中的 IAM 主体（用户、角色、root）只限制最大权限，不授予权限；不影响管理账户；不影响服务关联角色（SLR）；默认附加 FullAWSAccess。
    RCP成员账户中的资源（S3、STS、KMS、SQS、Secrets Manager 等支持的服务）为资源设置最大权限，例如"仅允许组织内主体访问"，实现数据边界（Data Perimeter）。不影响管理账户。
    Declarative Policy服务配置（如 EC2）声明式强制某些服务配置（如禁止公开 AMI、强制 IMDSv2），即使有新 API 也生效。
    Tag Policy标签规范标签键/值的大小写和取值；可配合强制（enforce）阻止不合规标签操作。
    Backup PolicyAWS Backup组织级统一备份计划。
    AI opt-out PolicyAI 服务退出 AWS 用你的数据改进 AI 服务。

    SCP 常见写法

    • Deny list（推荐）：保留 FullAWSAccess，再加显式 Deny。例：拒绝 cloudtrail:StopLogging、organizations:LeaveOrganization。
    • Allow list：移除 FullAWSAccess，只允许列出的服务。管理更繁琐。
    • Region 限制：aws:RequestedRegion 条件 + NotAction 排除全局服务（IAM、Organizations、CloudFront、Route 53、Support 等）。
    • 例外：通过 aws:PrincipalArn 条件放行特定管理角色（例如 Control Tower 执行角色）。

    IAM 策略评估逻辑

    显式 Deny？→ 拒绝→SCP / RCP 允许？→资源策略允许？→身份策略允许？→权限边界允许？→会话策略允许？→允许
    • 任何层级的显式 Deny 最终生效。
    • 同账户：身份策略或资源策略二者之一允许即可（受边界、SCP 限制）。
    • 跨账户：双方都要允许——对方账户的身份策略 且 本方资源策略（或通过 AssumeRole）。
    • 权限边界（Permissions Boundary）：限制委派管理员能创建的角色的最大权限（"允许开发者建角色但不提权"）。

    AWS Control Tower

    • 自动搭建 Landing Zone：Organizations + IAM Identity Center + Log Archive 账户 + Audit 账户 + 组织级 CloudTrail 和 Config。
    • 控件（Controls / 旧称 Guardrails）：
      • 预防性（Preventive）= SCP/RCP
      • 检测性（Detective）= Config 规则
      • 主动性（Proactive）= CloudFormation Hooks，在资源创建前检查
      另按强制级别分为 Mandatory / Strongly recommended / Elective。
    • Account Factory：标准化开账户（通过 Service Catalog）；AFT：用 Terraform 的 GitOps 开账户；CfCT：用 CloudFormation/SCP 定制。
    • 已有 Organizations 也可以启用 Control Tower 并逐个注册（enroll）现有账户。
    • 漂移（Drift）：在 Control Tower 外改了 SCP/OU 会导致漂移，需要 Repair。

    常用全局条件键

    • aws:PrincipalOrgID / aws:PrincipalOrgPaths：只允许本组织 / 某 OU 的主体。
    • aws:SourceVpce / aws:SourceVpc：只允许通过特定 VPC 端点访问（S3 bucket policy 常用）。
    • aws:SourceIp：只对公网请求生效，经 VPC 端点的请求不带公网源 IP（常见陷阱）。
    • aws:SourceArn / aws:SourceAccount：防止服务对服务的混淆代理。

    • aws:SecureTransport：强制 HTTPS。

    3.3 网络连通性（高频重点）

    VPC 互联方案对比

    方案传递路由CIDR 重叠规模/特点典型场景
    VPC Peering✗✗点对点，N 个 VPC 需 N(N-1)/2 条；无带宽瓶颈、无额外小时费；支持跨区域跨账户少量 VPC、高带宽低成本
    Transit Gateway✓✗（同一路由域内）Hub-and-spoke，多路由表实现隔离；支持 VPN ECMP、DX、跨区域 TGW Peering（静态路由）、Connect 挂载（SD-WAN，GRE+BGP）、组播大量 VPC + 本地网络
    PrivateLinkN/A（单向）✓服务提供方用 NLB/GWLB 建 Endpoint Service，消费方建接口端点；只能消费方发起SaaS、共享服务、CIDR 重叠
    VPC Lattice应用层✓服务网络（Service Network），L7 服务间通信、认证策略，跨账户微服务跨 VPC/账户通信，不想管网络路由
    Cloud WAN✓—基于策略的全球网络（Core Network），自动管理多区域 TGW 式连接和分段（Segment）全球多区域 + 分支机构 WAN

    VPC 端点

    • 网关端点（Gateway Endpoint）：仅 S3 和 DynamoDB；免费；通过路由表生效；无法从本地、对等 VPC、TGW 另一侧访问。
    • 接口端点（Interface Endpoint）：ENI + 私有 IP，按小时 + 流量计费；可从本地经 DX/VPN 访问；支持安全组；S3 也支持接口端点（本地访问 S3 私有路径的答案）。
    • 集中化接口端点：放在共享服务 VPC，通过 TGW 共享，配合 Route 53 私有托管区（关闭 private DNS，手动建 PHZ 并关联到各 VPC）以节省成本。

    Direct Connect（DX）

    VIF 类型连接目标说明
    Private VIFVGW 或 DX Gateway → VPC访问 VPC 私有 IP
    Public VIFAWS 公共端点访问 S3、DynamoDB 等公共 IP，可在其上搭建 IPsec VPN 实现加密
    Transit VIFDX Gateway → Transit Gateway大规模 VPC 接入
    • DX Gateway：全局资源，一条 DX 连接多个 Region 的 VGW/TGW；不能用于 VPC 之间互通（不提供 VPC 间传递）。
    • 连接类型：专用连接（Dedicated，1/10/100/400 Gbps，直接向 AWS 申请）、托管连接（Hosted，50 Mbps–25 Gbps，经合作伙伴）。开通通常需要数周 → 紧急场景先用 VPN。
    • 高可用：
      • 最高弹性（Maximum Resiliency）：2 个 DX 位置 × 每处 2 条连接（关键业务）。
      • 高弹性（High Resiliency）：2 个 DX 位置各 1 条连接。
      • 低成本备份：DX + Site-to-Site VPN 备份。
    • LAG：同一位置多条同速率连接捆绑（LACP）。
    • 加密：DX 本身不加密。可选 MACsec（L2，部分 10/100 Gbps 专用连接），或在 DX 上跑 IPsec VPN（Public VIF 或配合 TGW 的私有 IP VPN）。
    • SiteLink：通过 AWS 骨干网连接你的不同 DX 位置（分支互联），流量不进 Region。
    • BGP 选路：AWS 侧优先最长前缀匹配；本地可用 AS_PATH prepend、Local Preference（BGP community）控制主备。DX 路由优先于 VPN（相同前缀时）。

    Site-to-Site VPN

    • 每条 VPN 连接 2 条隧道，每条隧道最高约 1.25 Gbps。
    • 超过带宽：TGW + 多条 VPN + ECMP（需 BGP 动态路由）聚合。VGW 不支持 ECMP。
    • Accelerated VPN：经 Global Accelerator 边缘接入，改善远距离质量（仅 TGW 挂载）。
    • Client VPN：员工远程接入（OpenVPN 客户端）。
    • VPN CloudHub：VGW 连接多个分支，分支间可互通（hub-and-spoke）。

    混合 DNS（Route 53 Resolver）

    本地 → AWS

    本地 DNS 配置条件转发到 Inbound Endpoint 的 IP → 解析私有托管区（PHZ）和 VPC 内名称。

    AWS → 本地

    创建 Outbound Endpoint + Forwarding Rule（如 corp.example.com → 本地 DNS IP）；通过 RAM 把规则共享给其他账户的 VPC。
    • 跨账户关联 PHZ：PHZ 所在账户 create-vpc-association-authorization → VPC 所在账户 associate-vpc-with-hosted-zone（CLI/API，控制台不支持）。
    • 集中式 DNS：在网络账户集中部署 Resolver 端点，规则共享到所有 VPC。
    • Route 53 Resolver DNS Firewall：过滤出站 DNS 查询（阻止恶意域名、数据外泄）。

    集中出口与流量检查

    • 集中出口（Centralized Egress）：所有 Spoke VPC 默认路由指向 TGW → Egress VPC 的 NAT Gateway → IGW。节省 NAT 网关数量，但要注意跨 AZ 流量费和 TGW 数据处理费。
    • Inspection VPC：TGW 路由将流量引入检查 VPC（AWS Network Firewall 或 GWLB + 第三方防火墙）。必须在 TGW 的检查 VPC 挂载上启用 Appliance Mode，保证双向流量走同一 AZ（对称路由）。
    • GWLB：L3 网关 + L4 负载均衡，GENEVE 协议（6081 端口），用于透明插入第三方虚拟设备。
    • Network Firewall：托管有状态防火墙，支持 Suricata 规则、域名过滤（SNI/HTTP Host）、TLS 检查。

    其他网络知识点

    • VPC 共享（RAM 共享子网）：网络账户拥有 VPC，参与账户在共享子网中创建资源；减少 VPC 数量和 TGW 挂载，集中管理网络。
    • VPC IPAM：组织级 IP 地址规划、分配与审计，避免 CIDR 冲突。
    • NAT Gateway：AZ 级资源，高可用需每个 AZ 一个；不支持安全组。
    • Egress-only IGW：IPv6 出站。
    • Prefix List：在安全组/路由表中引用 CIDR 集合，可通过 RAM 共享。
    • Traffic Mirroring：复制 ENI 流量给 IDS 分析。VPC Flow Logs：只记录元数据（不含 payload）。

    4.2 业务连续性与灾难恢复

    RPO（Recovery Point Objective）= 可容忍丢失多少数据；RTO（Recovery Time Objective）= 可容忍多久恢复服务。

    Backup & RestoreRPO/RTO：小时级
    成本：最低
    仅备份数据，灾难时用 IaC 重建全部资源。
    Pilot LightRPO：分钟级 / RTO：数十分钟
    核心数据实时复制（DB 运行），应用服务器关闭或不存在，灾难时启动并扩容。
    Warm StandbyRPO：秒级 / RTO：分钟级
    完整环境以缩小规模运行，可处理少量流量，灾难时扩容。
    Multi-site Active/ActiveRPO/RTO：接近零
    成本：最高
    多区域同时承载生产流量。
    区分 Pilot Light 与 Warm Standby问自己：备用区域的应用层能否立即处理请求？能（哪怕规模小）→ Warm Standby；不能，需要先启动 → Pilot Light。

    4.3 安全控制设计

    KMS 要点

    • 密钥类型：AWS 拥有的密钥、AWS 托管密钥（aws/s3，不能改策略，不能跨账户共享）、客户托管密钥（CMK）（可控策略、轮换、跨账户）。
    • Key Policy 是必须的：没有 key policy 授权，IAM 策略也无效（除非 key policy 委托给账户 root 允许 IAM 控制）。
    • 跨账户使用：Key Policy 允许对方账户 且 对方账户 IAM 策略允许。
    • Grants：临时、程序化授权（如 EBS、RDS 内部使用）。
    • 直接加密最多 4 KB → 更大数据用信封加密（GenerateDataKey）。
    • 多区域密钥（Multi-Region Keys）：相同密钥 ID 和材料复制到其他区域，跨区域解密无需重新加密（DynamoDB Global Tables、跨区域加密数据）。
    • 加密的 EBS 快照/AMI 跨账户共享：必须使用 CMK 并共享密钥；AWS 托管密钥加密的快照需先用 CMK 重新加密复制。
    • 导入密钥材料（BYOK）、CloudHSM（单租户 HSM，你独占控制密钥，适合合规要求完全自主管理）、External Key Store（XKS）（密钥留在本地 HSM）。
    • 自动轮换：CMK 可开启自动轮换（可配置周期），旧版本材料保留以解密历史数据。

    数据保护

    • S3：Block Public Access（账户级/组织级）；默认 SSE-S3 加密；SSE-KMS（审计、权限控制，注意 KMS 请求配额，可用 S3 Bucket Key 降低 KMS 调用成本）；SSE-C；客户端加密。Object Ownership 设为 Bucket owner enforced（禁用 ACL）。
    • Object Lock：Governance 模式（有特殊权限可删除）vs Compliance 模式（任何人包括 root 都不能删除/缩短保留期）；Legal Hold 无期限保留。
    • Macie：发现 S3 中的 PII。
    • ACM：免费公有证书自动续期（ALB、CloudFront、API Gateway）；CloudFront 证书必须在 us-east-1。AWS Private CA：内部私有证书。
    • 传输加密：ALB/NLB TLS 终止；NLB TLS 透传（端到端加密，证书在后端）。

    边缘与应用防护

    • AWS WAF：部署在 CloudFront、ALB、API Gateway、AppSync、Cognito；托管规则组、速率限制规则、地理匹配、Bot Control、Fraud Control（账户接管防护）。

    • Cognito：User Pool（用户目录、OAuth/OIDC、MFA、社交登录）；Identity Pool（换取 AWS 临时凭证）；ALB 可直接集成 Cognito 认证。

    Auto Scaling 与负载均衡

    • 伸缩策略：目标跟踪（首选）、步进、简单、计划伸缩（可预测高峰）、预测性伸缩（ML 预测周期性负载）。
    • Warm Pool：预初始化实例，缩短启动时间。生命周期挂钩：启动/终止时执行脚本（如终止前上传日志）。
    • 混合实例策略：On-Demand 基础容量 + Spot 多实例类型，分配策略 price-capacity-optimized。
    • ALB（L7，路径/主机/Header 路由，Lambda 目标，认证）；NLB（L4，静态 IP/EIP，超高性能，PrivateLink 必需，保留源 IP）；GWLB（安全设备）。
    • 跨可用区负载均衡：ALB 默认开启；NLB/GWLB 默认关闭（开启会产生跨 AZ 费用）。
    • 健康检查：ASG 默认只用 EC2 状态检查，需启用 ELB 健康检查才能替换应用层不健康实例。

    Serverless 要点

    • Lambda：最长 15 分钟；内存最大 10 GB；预置并发（消除冷启动）；预留并发（限制/保证并发）；SnapStart（Java 等，减少冷启动）；VPC 内 Lambda 访问互联网需 NAT。超过 15 分钟的任务 → Step Functions、ECS Fargate、AWS Batch。
    • API Gateway：REST（功能最全：API Key/使用计划、请求验证、缓存、WAF、私有 API）vs HTTP（便宜、低延迟、JWT 授权）vs WebSocket；默认集成超时 29 秒；节流 429；端点类型 Edge-optimized / Regional / Private。
    • RDS Proxy：连接池，解决 Lambda 连接风暴；故障转移更快；可强制 IAM 认证。

    数据量 \ 带宽100 Mbps1 Gbps10 Gbps
    1 TB≈ 22 小时≈ 2.2 小时≈ 13 分钟
    10 TB≈ 9 天≈ 22 小时≈ 2.2 小时
    100 TB≈ 93 天≈ 9 天≈ 22 小时
    1 PB≈ 2.5 年≈ 93 天≈ 9 天

    7. 易混淆点与常见陷阱

    SCP 不授权

    SCP 只设定上限，用户仍需 IAM 策略授权。SCP 不影响管理账户——题目要"限制所有账户"时，管理账户不在其中。

    VPC Peering 不传递

    A↔B、B↔C 不代表 A↔C；也不能借对方的 IGW/NAT/VPN/DX 出去（edge-to-edge routing 不支持）。

    网关端点只在本 VPC 有效

    本地/对等 VPC 访问 S3 走私网 → S3 接口端点。

    DX ≠ 加密

    要求"加密 + 专线"→ MACsec 或 DX 上跑 VPN。

    DX 开通需要时间

    "下周就要"→ 先 VPN，DX 作为长期方案。

    Multi-AZ ≠ 读扩展

    RDS Multi-AZ 备用实例不可读（Multi-AZ DB Cluster 例外）；读扩展用只读副本。

    只读副本 ≠ DR 的同步保障

    只读副本异步复制，有 RPO；同步 HA 用 Multi-AZ。

    Firehose 不是实时

    有缓冲区（大小/时间），需要毫秒/秒级多消费者 → Kinesis Data Streams。

    AWS 托管 KMS 密钥不能跨账户

    跨账户共享加密快照/AMI → 必须使用客户托管密钥。

    CloudFront 证书在 us-east-1

    ALB 证书在 ALB 所在区域。

    Object Lock 模式

    Governance 可被特权用户绕过；"任何人都不能删除" → Compliance。

    aws:SourceIp 与 VPC 端点

    通过 VPC 端点访问时源 IP 是私网 IP，基于公网 IP 的条件会失效 → 用 aws:SourceVpce。

    Spot 不适合有状态关键负载

    除非有检查点/可中断设计；关键容量用 On-Demand + SP/RI。

    Savings Plans 不保证容量

    需要容量保证 → On-Demand Capacity Reservation 或 Zonal RI。

    Lambda 15 分钟

    长任务 → Fargate / Batch / Step Functions 拆分。

    安全组 vs NACL

    SG 有状态，只有 Allow；NACL 无状态，有 Deny，按规则号顺序评估，需放行临时端口（1024–65535）回包。封禁特定 IP → NACL 或 WAF。

    Pilot Light vs Warm Standby

    备用区应用是否正在运行。

    DataSync vs Storage Gateway

    DataSync = 迁移/同步数据；Storage Gateway = 本地应用持续使用云存储（混合）。

    MGN vs DMS

    MGN 迁移整个服务器（包括其上的数据库，同构）；要换数据库引擎或迁移到 RDS → DMS。

    Route 53 健康检查私有资源

    健康检查器在公网，无法直接检查私有 IP → 用 CloudWatch 告警作为健康检查依据。

    Q1. 一家公司使用 AWS Organizations 管理 120 个账户。安全团队要求：任何成员账户中的任何用户（包括 root）都不能停止或删除 CloudTrail 日志，也不能让账户离开组织。哪种方案运维开销最少？
    1. 在每个账户中创建 IAM 策略拒绝相关操作并附加给所有用户组
    2. 在组织根上附加一个 SCP，显式拒绝 cloudtrail:StopLogging、cloudtrail:DeleteTrail 和 organizations:LeaveOrganization
    3. 使用 AWS Config 规则检测 CloudTrail 是否停止并用 Lambda 重新启用
    4. 在每个账户中启用 CloudTrail 并配置 S3 Object Lock
    查看答案与解析
    答案：B。SCP 对成员账户的所有主体（包括 root）生效，附加在根上自动覆盖所有现有和新账户。A 无法约束 root 且需逐账户维护；C 是检测后修复而非预防；D 不能阻止停止日志记录。
    Q2. 一家公司在 3 个区域有 60 个 VPC，并通过 2 条 10 Gbps Direct Connect 连接本地数据中心。所有 VPC 需要互通并能访问本地网络，未来还将增加 VPC。哪种方案最具可扩展性？
    1. 在所有 VPC 之间建立 VPC Peering，并为每个 VPC 创建 Private VIF
    2. 在每个区域部署 Transit Gateway 并建立跨区域 TGW Peering；通过 Direct Connect Gateway 的 Transit VIF 将 TGW 连接到本地
    3. 使用一个 Direct Connect Gateway 关联所有 VPC 的 VGW，实现 VPC 间互通
    4. 在每个 VPC 中部署 EC2 软件 VPN 设备建立全互联
    查看答案与解析
    答案：B。TGW 提供传递路由与集中化管理，跨区域 TGW Peering 连接多个区域，Transit VIF + DXGW 接入本地。C 错在 DX Gateway 不支持 VPC 间流量传递；A 管理复杂且 Private VIF 数量有限；D 运维负担大。
    Q3. 本地应用需要解析 AWS 中 Route 53 私有托管区 aws.internal.example.com 的记录，同时 VPC 中的 EC2 需要解析本地域 corp.example.com。应该如何配置？（选两项）
    1. 创建 Route 53 Resolver 入站端点，并在本地 DNS 服务器上为 aws.internal.example.com 配置条件转发到入站端点 IP
    2. 将私有托管区改为公有托管区
    3. 创建 Route 53 Resolver 出站端点，并创建转发规则把 corp.example.com 转发到本地 DNS 服务器，关联到 VPC
    4. 在 VPC DHCP 选项集中把 DNS 服务器改为本地 DNS 服务器 IP
    5. 在 EC2 上部署 BIND 并在每台实例上修改 resolv.conf
    查看答案与解析
    答案：A、C。入站端点处理"本地 → AWS"，出站端点 + 转发规则处理"AWS → 本地"。B 暴露内部记录；D 会让 VPC 失去解析私有托管区和 AWS 内部名称的能力；E 运维开销大。
    Q4. 一家 SaaS 提供商需要将 API 服务提供给 300 个客户的 VPC，很多客户 VPC 的 CIDR 与提供商 VPC 重叠。客户只应访问该 API，不能访问提供商的其他资源。最佳方案是？
    1. 与每个客户 VPC 建立 VPC Peering
    2. 使用 Transit Gateway 连接所有客户 VPC
    3. 在 API 前放置 NLB，创建 VPC Endpoint Service（PrivateLink），客户在自己的 VPC 中创建接口端点
    4. 将 API 通过公网 ALB 暴露并使用安全组白名单
    查看答案与解析
    答案：C。PrivateLink 支持 CIDR 重叠、单向访问、只暴露特定服务，可扩展到大量消费者。A、B 不支持 CIDR 重叠且暴露更广的网络访问；D 走公网，不满足私有访问需求。
    Q5. 某金融公司使用 Aurora MySQL，要求区域级故障时 RPO 小于 5 秒、RTO 小于 5 分钟，同时希望在次要区域提供低延迟读取。哪种方案最合适？
    1. 每小时将 Aurora 快照复制到另一区域
    2. 创建跨区域 Aurora MySQL 二进制日志只读副本
    3. 使用 Aurora Global Database，在次要区域部署应用读取次要集群，故障时提升次要区域
    4. 使用 AWS DMS 持续复制到另一区域的 RDS MySQL
    查看答案与解析
    答案：C。Aurora Global Database 存储层复制延迟通常低于 1 秒，可在分钟内完成跨区域故障转移，次要集群支持本地读取。A 的 RPO 为小时级；B 基于 binlog 复制延迟和提升时间更不可控；D 增加运维且 RTO 较长。
    Q6. 公司需在 3 周内把 150 TB 文件数据从本地 NAS 迁移到 S3，出口带宽为 500 Mbps 且白天已有 60% 被业务占用。迁移期间文件仍会持续变化。哪种方案最合适？
    1. 使用 DataSync 通过现有网络传输所有数据
    2. 在该企业已具备 Snowball Edge 使用资格的前提下，订购多台 Snowball Edge Storage Optimized 设备复制初始数据，导入 S3 后使用 DataSync 同步增量变化
    3. 使用 S3 Transfer Acceleration 上传
    4. 申请 10 Gbps Direct Connect 后再用 DataSync 传输
    查看答案与解析
    答案：B。150 TB 在约 200–500 Mbps 可用带宽下需要 1–2 个月，无法满足 3 周要求。Snowball Edge 搬运初始数据，DataSync 负责增量与最终切换。D 中 DX 开通通常需要数周，来不及；C 不解决带宽瓶颈。
    Q7. 一家公司要将本地 Oracle 数据库迁移到 Aurora PostgreSQL 以降低许可成本，数据库包含大量存储过程，业务只能接受几分钟停机。应采取哪些步骤？（选两项）
    1. 使用 AWS SCT（或 DMS Schema Conversion）转换 Schema 和存储过程，并人工处理无法自动转换的部分
    2. 使用 AWS MGN 复制 Oracle 服务器
    3. 使用 AWS DMS 执行全量加载并开启 CDC 持续复制，切换时停止写入并修改应用连接
    4. 使用 Oracle Data Pump 导出并在 Aurora 中导入
    5. 使用 DataSync 复制 Oracle 数据文件到 S3
    查看答案与解析
    答案：A、C。异构迁移需先转换 Schema，再用 DMS 全量 + CDC 实现最小停机。B 只会把 Oracle 原样搬到 EC2，不改变引擎；D、E 不适用于异构目标且停机长。
    Q8. 公司计划在 6 个月内把数据中心中 800 台 VMware 虚拟机迁移到 AWS，要求尽量不改动应用，切换停机时间以分钟计。最合适的工具是？
    1. VM Import/Export
    2. AWS Application Migration Service（MGN）
    3. AWS DataSync
    4. 手动重建 AMI 并用 CloudFormation 部署
    查看答案与解析
    答案：B。MGN 提供持续块级复制、非破坏性测试和分钟级切换，适合大规模 Rehost。A 适合少量 VM 的一次性导入，停机长；C 迁移文件而非服务器；D 工作量巨大。
    Q9. 迁移前，架构师需要了解 400 台服务器（包含物理机和 VMware）之间的网络依赖关系，以便规划迁移波次。应使用什么？
    1. Application Discovery Service Agentless Collector
    2. 在所有服务器上安装 Application Discovery Service Discovery Agent，在 Migration Hub 中查看网络依赖
    3. VPC Flow Logs
    4. Migration Evaluator
    查看答案与解析
    答案：B。Discovery Agent 收集进程和网络连接数据，可得到依赖关系，并适用于物理机。A 仅适用于 VMware 且不提供进程级依赖；C 只用于 AWS 中的 VPC；D 侧重 TCO 业务案例。
    Q10. 一家全球在线游戏公司在 2 个区域运行基于 UDP 的游戏服务器。玩家客户端需要访问固定 IP 地址，并要求区域故障时快速自动切换。应使用什么？
    1. CloudFront 分发
    2. Route 53 延迟路由 + 健康检查
    3. AWS Global Accelerator，终端节点组指向两个区域的 NLB
    4. 每个区域使用弹性 IP，客户端内置两组 IP
    查看答案与解析
    答案：C。Global Accelerator 支持 UDP、提供静态 Anycast IP，并基于健康检查秒级切换，不受 DNS 缓存影响。A 不支持 UDP；B 不提供固定 IP 且受 TTL 影响；D 需要客户端逻辑。
    Q11. 合规要求本地数据中心到 AWS 的所有流量都必须加密，公司已有 10 Gbps 专用 Direct Connect 连接，需要尽量保持高吞吐。最佳方案是？
    1. 改用互联网上的 Site-to-Site VPN
    2. 在支持的 DX 位置和设备上启用 MACsec
    3. 依赖 Direct Connect 默认加密
    4. 在应用层改用 HTTP
    查看答案与解析
    答案：B。MACsec 在二层提供线速加密，适合 10/100 Gbps 专用连接。C 错误：DX 默认不加密；A 每隧道约 1.25 Gbps，吞吐不足；D 不安全。若设备不支持 MACsec，可在 DX 之上建立 IPsec VPN（结合 TGW ECMP 扩展吞吐）。
    Q12. 开发团队需要自助创建符合公司标准的 EMR 集群和 RDS 数据库，但安全团队不希望授予开发者创建这些资源的直接 IAM 权限。哪种方案最合适？
    1. 为开发者授予 AdministratorAccess 并用 Config 审计
    2. 使用 AWS Service Catalog 发布产品，设置 Launch Constraint 指定一个具备必要权限的 IAM 角色，并只授予开发者访问组合（Portfolio）的权限
    3. 让开发者向运维团队提交工单
    4. 使用 CloudFormation StackSets 部署所有可能的资源
    查看答案与解析
    答案：B。Service Catalog 的 Launch Constraint 让资源由指定角色创建，开发者仅需 Service Catalog 权限即可自助、合规地部署。
    Q13. 某公司计算支出稳定在每小时约 50 美元，但计划在一年内将部分 EC2 工作负载迁移到 Fargate 和 Lambda，同时可能更换实例族和区域。哪种购买方式最具成本效益？
    1. 3 年 Standard RI
    2. EC2 Instance Savings Plans
    3. Compute Savings Plans
    4. Spot 实例
    查看答案与解析
    答案：C。Compute Savings Plans 适用于任意实例族、区域、OS，并覆盖 Fargate 与 Lambda，最适合计划变化的场景。A、B 绑定实例族/区域；D 不适合稳定的关键负载。
    Q14. 公司有 40 个 Spoke VPC 通过 Transit Gateway 互联，需要对所有 VPC 间流量和出站互联网流量进行有状态检查。部署 AWS Network Firewall 后发现部分连接被丢弃。最可能的原因和修复是？
    1. Network Firewall 不支持 TGW，需改用 VPC Peering
    2. 在 Inspection VPC 的 TGW 挂载上未启用 Appliance Mode，导致非对称路由；启用 Appliance Mode
    3. 需为每个 Spoke VPC 部署 NAT Gateway
    4. 需要将安全组改为 NACL
    查看答案与解析
    答案：B。没有 Appliance Mode 时，TGW 可能将去程和回程流量送到不同 AZ 的防火墙端点，有状态检查会丢弃这些"半连接"。
    Q15. 一家公司有 2,000 台 EC2 Linux/Windows 实例分布在多个账户，安全团队要求每月按计划打补丁并提供合规报告，且禁止开放 SSH/RDP 端口。最佳方案是？
    1. 使用堡垒机手动登录打补丁
    2. 使用 Systems Manager Patch Manager 配置补丁基线与维护窗口，借助 Session Manager 在需要时访问实例，通过 Patch 合规报告和 Explorer 汇总
    3. 每月用新 AMI 替换所有实例
    4. 在用户数据中添加 yum update 并每月重启实例
    查看答案与解析
    答案：B。SSM Patch Manager 和 Maintenance Window 实现规模化补丁与合规报告；Session Manager 无需开放入站端口。C 对不可变架构可行，但对 2,000 台异构实例运维成本高且不提供合规报告。
    Q16. 监管要求某些交易记录保存 7 年，期间任何人（包括账户 root）都不能删除或覆盖。数据存储在 S3，读取频率极低。最具成本效益的方案是？
    1. S3 Standard + 版本控制 + MFA Delete
    2. 启用 S3 Object Lock Compliance 模式，保留期 7 年，并使用生命周期规则将对象转为 Glacier Deep Archive
    3. Object Lock Governance 模式 + S3 Standard-IA
    4. 使用 IAM 策略拒绝 s3:DeleteObject
    查看答案与解析
    答案：B。Compliance 模式下任何人都无法删除或缩短保留期；Deep Archive 成本最低。C 的 Governance 可被特权绕过；A、D 均可被 root 或管理员更改。
    Q17. 某 Serverless 应用使用 API Gateway + Lambda + RDS PostgreSQL。促销活动期间出现大量 "too many connections" 错误，数据库 CPU 并不高。改动最小的修复是？
    1. 将 RDS 实例升级到更大规格
    2. 部署 RDS Proxy，并让 Lambda 连接代理端点
    3. 改用 DynamoDB
    4. 将 Lambda 预留并发设为 1
    查看答案与解析
    答案：B。问题是连接数而非算力，RDS Proxy 对连接进行池化和复用。A 只能小幅提高 max_connections；C 需重构；D 会严重限制吞吐。
    Q18. 某公司希望保证组织中所有 S3 存储桶只能被本组织内的 IAM 主体访问（AWS 服务代表本组织访问的情况除外），即使某个账户管理员错误地在 bucket policy 中授予了外部账户访问。哪种方案最适合并能自动覆盖新账户？
    1. 在每个存储桶的 bucket policy 中加入 aws:PrincipalOrgID 条件
    2. 在组织根上附加 Resource Control Policy（RCP），拒绝 aws:PrincipalOrgID 不等于本组织 ID 的主体访问 S3（并为 AWS 服务主体设置例外）
    3. 使用 SCP 拒绝 s3:PutBucketPolicy
    4. 用 Macie 定期扫描公开存储桶
    查看答案与解析
    答案：B。RCP 在资源侧设定最大权限，集中强制数据边界，无论单个 bucket policy 如何配置，并自动覆盖新账户。A 需要逐桶维护且可被管理员修改；C 会阻碍正常运维；D 只是检测。
